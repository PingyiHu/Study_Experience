# 微软项目介绍

Owner: 吉祥 郑

# 基本介绍

- 采用两个Agent A、B针对一个问题进行回答，A负责主要解答问题，B负责评估A的解题思路，并给出新的建议。
- A和B背后的模型是不同的，A是qwen2.5-7B-Instruct，B是llama3.1-8B-Instruct，他们各自有一个system prompt以及对话历史的上下文
- 基本流程：
    - A首先给出针对问题的初始答案，并将内容发送给B
    - B针对A的信息，给出反馈：是否同意A的方案并给A新的建议
    - A收到B的反馈后，生成新的答案，再决定是否继续向B寻求帮助或是输出答案
- 采用的强化学习方法是改进的GRPO：
    - 奖励函数分为llm based和rule based，存在一个judge模型C，针对A和B的对话流程对每一轮对话进行评价
    - loss聚合方式采用DAPO的token mean
        - 原始短序列的总体梯度贡献和长序列的总体梯度贡献等同，使得长序列per token的梯度贡献被稀释，使得较长的无意义回复受到更少惩罚；使得较长的优秀推理pattern得到更少的奖励。短序列的per token loss高，会使得该token的概率值上升更快。
        - 得到每个样本归一化优势之后，会把这个优势复制到每一个token上，优势乘以重要性采样参数可以得到per token的loss
        - **sequence mean token mean：**每一个token的策略梯度loss，首先在序列内部对单条序列长度求平均，再在组内的序列之间对group数求平均
        - **token mean：**是per token loss对一个group内的总token数进行平均，每个token的权重相同，长序列可以得到更多的重视
    - 采样过程中使用动态课程学习，保证题目难度时刻和模型能力匹配
    - 支持多种训练顺序

# 奖励设置

- A和B都有格式奖励和正确性奖励
- 同时A和B还有一个额外的惩罚项，让A能够采纳B的意见，让B不轻信A
    - 通过一个特殊的tag实现，B返回信息的时候，会显式地给出一个tag，表示其对A的做法是否同意
- 同时对于A和B的每一轮对话，会有一个额外的模型C给出一个额外的奖励，评判交流的质量
- 对于规则奖励，进行组内归一化；对于多轮对话，进行段内归一化

# 为什么研究多Agent的GRPO

- **熵坍塌慢：**尝试过单Agent生成回复，模型反思之前生成的答案并给出新的答案，由于答案的生成和反思均由单一模型完成，模型的回复分布很快就集中到高置信区域，熵坍塌很快（具体表现为后续轮次反思得到的回复和之前是差不多的）；多Agent的情况下，Agent B需要对Agent A进行质疑，相比单agent的情况，更难达成一致，熵降低慢
- **细粒度奖励：**Agent A和Agent B的来回交互的场景下，可以使用LLM对每一轮回复进行更细粒度的回复打分，使得一些优秀的思考pattern得到更多的优化
- **回复多样性：**能够获取对于单一问题多个角度的回答
- **更加容易扩展到无标签情况：**AgentB可以再进一步优化为一个回复的打分器，针对无标签的场景，可以给Agent A优化指导，相比reward model的优势在于：
    - 可以给出细粒度的打分，而不是像reward model只可以给一个段的内容打分
    - B可以实时的看到A当前的输出分布，reward model只是离线地看到部分人类的偏好
    - LLM给出的分数更加具有可解释性

# 使用的是什么数据，怎么处理的

- **名字：**使用的数据是DAPO-math-17K，是一个比较困难的数学问题数据集
- **分难度：**对于每一个问题，使用base model进行16次回复生成，并根据准确率高低划分为5个等级，每个等级的样本数量尽可能接近
- **初始的分布：**正确率过高或过低的比例较低，难度中档的题目占大多数
- **滑动窗口：**每个等级都有一个滑窗，根据每个等级的题目当前的正确率，动态调整题目的分布 ，保证总体正确率在50%左右
    - 记录每个等级题目正确与否
    - 前10个step保持初始分布不变，填充每一个等级的滑动窗口
    - 计算所有难度等级的滑动窗口的正确率，以及当前的平均正确率
    - 根据每个等级的正确率调整难度分布

# 对于VERL框架修改了哪些部分

- **奖励计算**：添加了一个reward model的server可以对每一轮生成的回复进行细粒度打分
- **每一个会话的轮次不同，每一轮生成的内容长度不同，我们需要对会话的状态和整个rollout的过程进行管理，新的rollout worker**：
    - 记录A和B针对某一个问题的会话：
        - 追踪当前会话的状态
        - agent的上下文，mask用于标记上下文中由A或B生成的部分
        - 各自的采样参数
        - 剩余的对话token预算
    - 规范化A和B的对话流程，对不符合要求的会话进行早停
- **会话token上限：**将VLLM rollout的单次生成token上限，修改为会话生成的token上限，保证与其他方法的公平比较
- **动态难度：**更改了数据集加载的方式，可以动态改变当前batch的难度分布
- **不同的训练方式：**支持AB同时训练，或是AB交替训练，同时兼容DAPO的buffer，可以过滤特定指标完全相同的batch

# 针对熵坍塌做了哪些优化

- 使用两个差异较大的模型，例如llama，其初始的熵就很高
- 加上了熵相关的loss
- random truncate：由于缺失了某部分内容之后，语言模型还是能猜出剩下的内容的，因此在进行信息传递时，对信息进行随机缺失，这样信息传到另一个agent的时候，context就不同，之后的生成过程也会不一样
- 错误样本再利用：对于模型生成的错误回复，将其也作为prompt的一部分，告知模型之前生成的内容有误，让其重新生成回复。相当于人为地进行了一个转折，这样一来模型就有可能做对，不会全错
- 只要使得难度和模型匹配的方法，都算是减弱熵坍塌的这个现象。
    - 保存ckpt，在熵明显降低的时候，切换训练数据集
    - 使用课程学习、动态课程学习

# 有遇见什么困难吗

- eos token需要被奖励：
    - 由于对话有多轮，并且涉及到交互，因此我们**自己定义了一系列的tag**，作用是标定问题、当前agent生成的信息、其他agent传送的信息以及对话的结束
    - vllm采样参数中的**stop可以指定生成到特定的tag之后结束生成**，但是指定了特定的tag之后，eos就没有生成
    - 这就导致了进行策略梯度优化的时候**eos没有被奖励，使得模型生成的内容越来越长，并且重复的信息开始变多**，原因：
        - tag不是一个单独的token，由于采样的存在，因此会导致结束的tag不正常，没法正常结束，如果这个不正常的结束tag之后又出现了一个正常的结束tag，相当于是给了模型一个信号，生成的越长越好
        - 模型在预训练的时候学过结束的标签就是eos，把eos和我自定义的结束符号绑定在一起之后，模型就知道了生成自定义的结束标签就约等于生成eos
- **qwen学了很多开源数据集的优秀CoT**：直接采用一些开源的数据集，比如math这样的数据集，模型很快就会停止进步了（我们把常见的数据集的内容，直接输入到qwen base中，发现针对每一个问题，都有格式相近的完整cot）
    - 在这样的数据集上qwen的能力已经很强了，**题目的难度不匹配**，group内要么是全对要么是全错，真正有效的样本很少
    - 解决措施：
        - 刚开始的时候使用**保存ckpt**，如果正确率很久不变的话，**就改变训练集**（math，omini-math，gsm8k，DAPO-math）
        - **使用DAPO**，训练时间拉长了很多，因为里面的难题不论怎么样都做不出了，因为难度提高的太快了，不平滑
        - 使用一个**难度分级的数据集**，并且在训练的过程中动态地改变batch内的难度分布，使得模型在这个batch上的准确率尽可能接近百分之50
- **reward hijack**：
    - 轮次奖励：一开始的时候认为**讨论的轮次越长，是不是效果越好**，结果加入了轮次奖励之后，即使是一个饱和很快的指数奖励，也会使得模型不断地增加讨论轮次，直到超出回复的上限
    - reward越简单越好，只要模型有利可图，就会不断往有利可图的方向更新，越复杂的规则奖励，空子越多
    - 最好的奖励就是简单的规则奖励，加上LLM as a judge，这个奖励不能超过规则奖励的任何一项，防止模型欺骗奖励
- 保证A和B**不会过分依赖对方**，引入制衡的惩罚：
    - A每一轮都会给出一个临时的答案
    - Agent B会对当前的AgentA的回复给出其是否认可。如果A不得到认可直接输出，会被惩罚
    - Agent B如果仅仅是同意A的答案，而A最后回答错误，则B会受到惩罚
- **base model怎么接受一段很长的system prompt**：system prompt很长，但是我们定义的格式是不使用chat template的，因此用base model进行训练不大训得起来，所以先自己构造了一些简单的格式正确的样本对base model进行SFT之后，再进行RL
- **熵坍塌**，见上

# 多轮对话的SFT怎么训

[(4 封私信) 多轮对话的训练过程详解 - 知乎](https://zhuanlan.zhihu.com/p/695202364)

- 方式1：只有最后一轮agent的输出进行权重更新，其他轮的用户输入和agent输出仅作为输入
- 方式2：将n轮对话拆成n组输出进行训练
- 方式3：在对话的数据中，只对agent输出部分进行backward
    - 对当前轮的agent输出进backward的时候，反正是看不到后续的输入输出的

# VLLM server是如何准确的把某个请求的响应发送给对应的设备的？

每个rank都会使用临时端口给server发送一个请求，并与server建立连接

server只需要根据各个rank的临时端口，将回复发送回来即可

# Agent toolcall的做法

[(7 封私信) DeepSearch复现篇：QwQ-32B ToolCall功能初探，以Agentic RAG为例 - 知乎](https://zhuanlan.zhihu.com/p/30289363967)

```python
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    StoppingCriteria,
    StoppingCriteriaList
)

tool_call_regex = r"<tool_call>(.*?)</tool_call>\s*$"
end_regex = r"<\|im_end\|\>\s*$"

# 同时监测: <tool_call> 或 <|im_end|>
class RegexStoppingCriteria(StoppingCriteria):
    def __init__(self, tokenizer, patterns):
        self.patterns = patterns
        self.tokenizer = tokenizer

    def __call__(self, input_ids: torch.LongTensor, scores: torch.FloatTensor, **kwargs) -> bool:
        decoded_text = self.tokenizer.decode(input_ids[0])
        for pattern in self.patterns:
            if re.search(pattern, decoded_text, re.DOTALL):
                return True
        return False

stopping_criteria = StoppingCriteriaList([
    RegexStoppingCriteria(
        tokenizer,
        patterns=[tool_call_regex, end_regex]
    )
])

model.generate(..., topping_criteria=stopping_criteria) # 加上停止符
```

# 两个Agent是怎么训练的，前向和反向的过程是什么样的

verl中有3类batch size：

- micro batch，实际在gpu上进行反向传播计算的batch大小
- mini batch，梯度累计，micro batch累积到一个mini batch大小的时候，会更新一次模型
- batch，实际的batch size。
- batch分mini batch是为了重要性采样，减少了load模型的次数，采样一次更新多次，提高更新的效率

由于A和B的整体过程类似，此处仅对agent A的整体过程进行描述

- 模型的采样使用vllm
- 模型的前向和更新使用的是hugging face格式的模型
- 更新结束之后，会将HF格式的权重同步到VLLM

## rollout加载部分

- 每个ActorRolloutRefWorker负责一个agent的采样和更新
- worker group中初始化两个自定义的ActorRolloutRefWorker
    - 每次对actor model进行更新之后，需要更新rollout model，也就是把当前的模型的权重拷贝到vllm engine中
    - 将B的vllm engine权重更新之后，送入A的worker中，这样A和B就可以在rollout的过程中进行交流

## rollout生成部分

- A生成的内容分为think、question、answer三个模块
- 模型生成到question模块的时候，会检测question的结束标签是否生成，并用正则匹配的方式检验：**当前的question是否有一个开始的标签**
- 提取question之间的内容，加入到B的上下文中，随后开始B的内容生成
- 将B的内容以类似的方式再append到A的question block之后

## 奖励计算

### rule based部分

- 检测tag：
    - 是否两两匹配
    - 顺序是否正确
- 检测答案：对最后一个回复中的**latex boxed**信息进行提取，使用math verify进行验证
    - math verify是一个可以答案判别库，可以更智能的进行答案匹配，如0.5可以和1/2进行匹配
- 根据最后一个B发送的显式标签以及最终答案是否正确，给出制衡惩罚
- 更新当前batch上的综合正确率，方便dataloader的sampler实时更新batch难度分布
- 归一化组内奖励，计算得到advantage

### LLM as a judge部分

- 使用agent C给出每一段的细粒度分数，要求打分的数量等于段落个数，否则重新生成

## 前向logits再计算

虽然VLLM可以计算log probability但是由于存在加速算子，可能使得计算得到的log prob和直接使用huggingface格式的模型进行前向的模型差别很大（有的人可能会想用VLLM计算**old log probs**）：

- 计算采样到的回复的每一个token的log probs：
    - 使用HF格式的model重新进行前向计算，得到最后一层的pre softmax logits
    - 计算当前位置对应token的log probs
- mini batch每更新一次都会重新计算一次log probs，从而获取重要性采样参数

## Loss

- 对advantage乘以logprobs进行梯度上升，就是对负的advantage乘以logprobs进行梯度下降。
- 对于非当前agent生成的内容，直接对advantage置零处理，这些token不进行优化
- 每一个位置都有一个log probs和advantage，需要聚合loss，loss聚合的方式使用token mean，将per token的loss在整个batch level进行平均

# 课程学习是如何动态改变难度的，指标是什么？

- 根据不同难度的正确率，将题目分为simple level和hard level两级
    - 正确率大于百分之50为hard level
    - 正确率小于百分之50为easy level
- 根据当前的综合准确率，采取小步长，如果题目过难将分布朝着简单方向移动
- 如果所有的题目的准确率均小于百分之50，说明当前训练集难度过高，会将一个简单题优先分布，比如一个概率值根据当前等级指数递减的分布，与先验经验分布进行加权，强制将难度等级降低

# 测试集指标

- 两个模型分别是qwen2.5-7B-Instruct
- 在DAPO-math-17K上进行训练
- AVG@16正确率：
    - 意义是每个问题采样16次，计算所有问题上的平均正确率
    - 未经训练的qwen2.5-7B-Instruct的AVG16正确率为15%
    - 单agent GRPO的AVG16正确率为18%
    - 单agent DAPO的AVG16正确率为20%
    - 双agent协作的AVG16正确率为23%
- 时延：在实际测试中，整体延迟大约是单模型 baseline 的**2–3 倍**，具体取决于group大小、序列长度。
    1. 多候选采样带来的推理时长增加；
    2. judge 模型的额外评估；
    3. 不同模型间通信与调度的少量开销。
