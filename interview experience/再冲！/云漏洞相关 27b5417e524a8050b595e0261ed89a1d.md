# HTTP

## 三次握手

为了让服务器和客户端都相互确认彼此存在并且已经收到了信息

- 第一次syn，告知服务器：客户端存在、客户端的初始包编号k
- 第二次syn+ack，告知客户端：服务器收到；并给出服务器的初始包编号：
    - syn占用一个序号，因此服务器的ack会是k+1
- 第三次，告知客户端，初始序号已经获取，连接建立

## 四次挥手

1. **FIN**（主动关闭方 → 被动方）
2. **ACK**（被动方 → 主动方）—确认对端 FIN，**此时形成半关闭**（被动方仍可发数据）。
3. **FIN**（被动方 → 主动方）—当它也发完数据，开始关闭自己的发送方向。
4. **ACK**（主动方 → 被动方）—确认对端 FIN，连接完全关闭。主动关闭方进入 **TIME_WAIT**。
    - **SYN/FIN 各占 1 个序号**；纯 **ACK 不占**。
    - 若两端恰好没有待发送数据，步骤 **(2) 和 (3)** 可能合并为一个 **FIN+ACK**（线包 3 个，但语义仍是四步）。
    - 为什么要time wait，因为对于fin的ack可能会丢失，从而对端不断超时重传fin

# SSRF（Server-Side Request Forgery）

服务端请求伪造：攻击者诱导服务器发起本不应该发起的网络请求，去访问内网的敏感资源

## 发生攻击的原因

有一些服务器提供查询的端口，我们可以让服务器为我们进行某些IP地址的访问：

- 用户输入的请求是朝外网收集信息，那完全没问题
- 如果用户输入的信息是收集内网数据，如果服务器没有做防护，就可能暴露内网的敏感信息，例如内网的拓扑

# CSRF

利用网站对浏览器的信任：

- 用户之前登录过某个网站，保留下了cookie
- 如果用户登录的某个网站存在一个链接，这个链接会借用这个cookie，完成对用户身份的验证
- 在未经用户同意的情况下，使得某些需要授权的行为被执行

**防御方法**

- 在http请求中加入验证字段，检验是什么网站发起的请求
- 增加验证码

# XSS

恶意用户在网站可以进行输入的位置（比如评论区），输入的不是正常的文本，而是输入一段java script，这个脚本被保存在服务器上

评论发布之后，正常的用户访问网页，自动触发该脚本，从而使得用户的信息被窃取

# SQLI

将用户可控的输入和服务器中提供的SQL语句相结合，从而改写查询的语义

```python
# 易受攻击：
sql = f"SELECT * FROM users WHERE name = '{user}' AND pass = '{pwd}'"
# 输入： user = ' OR '1'='1  ，pwd = anything
# 实际执行：
# SELECT * FROM users WHERE name = '' OR '1'='1' AND pass='anything';

```

# 反序列化漏洞

Java 对象序列化是 将 Java 对象的状态转换为字节数组，以便存储或传输的机制；以后，仍可以将字节数组转换回 Java 对象原有的状态。

如果我们传输的序列化数据中途被截获，截获方通过反序列化就可以获得里面的数据（**敏感数据的泄露**），甚至对里面的数据进行修改然后发送给接收方（**无法确保数据来源的安全性**）。
